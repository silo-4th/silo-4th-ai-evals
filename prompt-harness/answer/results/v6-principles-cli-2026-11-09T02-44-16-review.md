```sql
LAST_VALUE(ENAME) OVER (
  ORDER BY HIREDATE

```

<details><summary>답 532자</summary>

`ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`처럼 프레임의 끝을 `UNBOUNDED FOLLOWING`(맨 마지막 행)까지 넓혀서 쓰면 돼요. 그러면 프레임이 파티션 전체가 되어 모든 행에서 진짜 마지막 값이 나와요.

```sql
SELECT ENAME, HIREDATE,
       LAST_VALUE(ENAME) OVER (
         ORDER BY HIREDATE
         ROWS BETWEEN UNBOUNDED PRECEDING
                  AND UNBOUNDED FOLLOWING
       ) AS LAST_ALL
FROM EMP
WHERE DEPTNO = 10
ORDER BY HIREDATE;
```

10번 부서에서는 모든 행의 LAST_ALL이 마지막 입사자인 서인턴이에요. 시작은 `UNBOUNDED PRECEDING`이 아니라 `CURRENT ROW`로 해도 끝만 맨 마지막이면 마지막 값은 같아요.

### history02 (history, 단원 s2-05) 통과

**질문:** 그러면 HAVING에 DEPTNO = 10 같은 일반 조건을 써도 돼요?

**앞 대화(앞 답은 이 버전이 CLI에서 실제로 쓴 답):**

> [학습자] WHERE랑 HAVING 차이가 뭐예요?
>
> [AI] WHERE는 그룹으로 묶기 전에 행을 거르고, HAVING은 묶은 뒤에 그룹을 걸러요. SQL 처리 순서가 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY라서 이런 차이가 생겨요. WHERE를 처리하는 시점에는 아직 그룹이 없어서 SUM이나 AVG 같은 집계 값도 없어요. 그래서 집계 함수를 쓰는 조건은 HAVING에 써야 하고, WHERE에 쓰면 ORA-00934 오류가 나요.

예를 들어 `WHERE DEPTNO = 10`은 10번 부서 행만 남긴 뒤 묶고, `HAVING AVG(SAL) >= 4000`은 묶어서 평균을 낸 다음 4000 미만인 그룹을 빼요.

참고: 3. WHERE와 HAVING


**기대 행동(labels-draft):** 앞 대화를 이어받아, GROUP BY에 쓴 컬럼 조건이면 HAVING에 써도 동작하지만 묶기 전에 거르는 WHERE에 쓰는 것이 자연스럽다는 취지로 답한다. 단원 내용과 어긋나지 않는다.

**AI 판정:**

| 기준 | 판정 | 근거 |
|---|---|---|
| 정확성 | 통과 | GROUP BY에 쓴 컬럼은 HAVING에 쓸 수 있고, 그렇지 않은 컬럼은 ORA-00979 오류가 난다는 설명이 Oracle 문법에 맞아요. 결과가 같다는 설명도 맞아요. |
| 질문에 답함 | 통과 | '써도 되냐'는 물음에 '된다'고 바로 답했고, 조건과 권장 방식만 짧게 덧붙였어요. |
| 단원 근거 | 통과 | 단원에서 직접 다루지 않은 내용이라고 밝혔고, 단원의 SELECT 규칙과 처리 순서를 근거로 설명해 단원과 어긋나는 내용이 없어요. |
| 기대 행동 | 통과 | 앞 대화를 이어받아 HAVING에 써도 동작하지만 WHERE에 쓰는 게 자연스럽다는 기대 행동대로 답했어요. |

단원에서 직접 다루지 않은 내용인데, 문법상으로는 돼요. 다만 HAVING에는 그룹마다 값이 하나로 정해지는 것(GROUP BY에 쓴 컬럼, 집계 함수)만 쓸 수 있어요. 그래서 `GROUP BY DEPTNO HAVING DEPTNO = 10`처럼 GROUP BY에 쓴 컬럼이면 결과는 같아요. 하지만 GROUP BY에 없는 컬럼(예: ENAME)을 HAVING 조건에 쓰면 SELECT에서와 같은 이유로 오류가 나요.

MySQL에서는 쿼리 맨 끝에 `LIMIT 행수`를 붙이면 결과를 그 개수만큼만 가져와요. 보통 `ORDER BY` 뒤에 써요.
