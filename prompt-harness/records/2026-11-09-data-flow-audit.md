# 프롬프트 참고 데이터 설계 확인 (2026-11-09)

공유 문서의 "프롬프트가 참고하는 데이터"와 하네스의 입력 가정을, 개발 저장소와 Linear 기획에 대조한 결과입니다. 저장소와 Linear는 읽기만 했습니다.

- 저장소 기준: `cb5cd23` (develop, 11/9 10:22, 4-104 병합). 하네스를 만들 때 기준은 `a2a3970`(11/8)입니다.
- Linear 기준: 원칙 "이슈와 결정사항 문서가 다르면 문서를 따른다"에 따라 「스프린트1_결정사항 (최신 기준)」(11/9 수정)을 우선했습니다.

## 1. 결론

참고 데이터 설계는 대체로 맞습니다. 태그 이름, 순서, 모델, 제한 시간, 출력 형식은 코드와 일치합니다. 다만 아래 다섯 가지는 하네스나 공유 문서에 반영하거나, 기획에서 정해야 합니다.

1. **채점 checklist는 `keyPoints`에 기대는데, `keyPoints`를 없애기로 한 회의 결정이 있습니다.** 4-90: "11/6 회의에서는 keyPoints를 없애기로 했지만, 지금 코드의 검사와 채점이 쓰고 있어 당분간 유지해요." 기준 B로 정하면 퀴즈 생성이 핵심 요소를 3개 이상 만들어야 합니다(4-99).
2. **답변 프롬프트는 4-65에서 따로 쓰고 있습니다(11/9 점심 마감).** 원칙 5가지, 빠른 질문, 드래그 메뉴, 말투 지시문이 들어갈 예정입니다. 우리 v3-grounded와 합쳐야 하고, 원칙 일부는 지금 입력에 없는 데이터(과거 질문 날짜, 절 번호와 제목, 드래그한 문장)가 필요합니다.
3. **퀴즈 생성 경로가 세 개입니다.** 퀴즈 탭, 관련 문제 풀어보기 외에 꺼내 먹기(cb5cd23에서 추가)가 같은 프롬프트를 씁니다. 꺼내 먹기는 빈 맥락이 많고, 실패하면 기본 문제로 대신합니다.
4. **답변의 앞 대화와 과거 요약은 단원으로 거르지 않습니다.** 하네스는 2턴 대화와 같은 단원 요약만 시험했습니다. 긴 세션과 다른 단원 대화가 섞이는 경우는 시험하지 않았습니다.
5. **기본 문제를 세 형식으로 등록하는 계획은 Linear에 반대 기록이 있습니다.** 4-90: "모두 객관식이어도 돼요(11/5 회의)." 사용자 결정(11/9)으로 바뀌었으므로 Linear에 새 결정을 남겨야 합니다. 퓨샷 사용 여부는 4-80의 미정 항목입니다(`quiz-schema.md:390`).

## 2. 기능별 대조

## 4. Linear에 남겨야 할 결정 (사용자가 직접 기록)

- 기본 문제를 객관식, 빈칸, 서술형으로 나눠 등록한다(11/9, 4-90의 11/5 결정을 바꿈).
- 학습과 무관한 입력이면 keywords를 비운다(11/8).
- 답변의 단원 밖 처리와 길이 상한, 객관식 보기 순서를 코드로 섞는 것은 우리 제안이다. 4-65, 4-80에서 채택 여부를 정한다.
- 퓨샷 시험 결과(4-80 케이스 8): 목업 기준으로는 넣지 않는다. 형식별 기본 문제 등록 뒤 다시 시험한다.
