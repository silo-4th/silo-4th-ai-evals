<details><summary>AI 답 466자</summary>

거르는 시점이 달라요. WHERE는 그룹으로 묶기 전에 행을 거르고, HAVING은 묶은 뒤에 그룹을 걸러요. SQL 처리 순서가 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY라서 그래요.

그래서 WHERE를 처리할 때는 아직 그룹이 없어 SUM이나 AVG 같은 집계 값도 없어요. 집계 함수를 쓰는 조건은 HAVING에 써야 하고, WHERE에 쓰면 ORA-00934 오류가 나요.

```sql
SELECT JOB, AVG(SAL)
FROM EMP
WHERE DEPTNO = 10        -- 묶기 전: 10번 부서 행만 남김
GROUP BY JOB
HAVING AVG(SAL) >= 4000; -- 묶은 뒤: 평균 4000 이상인 직무만 남김
```

이 SQL에서는 WHERE가 박영업(20번 부서)을 먼저 빼고, HAVING이 평균이 3666.7인 DEV 그룹을 빼요.

</details>

<details><summary>AI 답 473자</summary>

`(+)`가 붙지 않은 쪽을 기준으로 LEFT 또는 RIGHT OUTER JOIN을 쓰고, 조인 조건은 WHERE가 아니라 ON에 써요.

```sql
-- Oracle (+)
SELECT D.DEPTNO, D.DNAME, E.ENAME
FROM DEPT D, EMP E
WHERE D.DEPTNO = E.DEPTNO(+);

-- ANSI
SELECT D.DEPTNO, D.DNAME, E.ENAME
FROM DEPT D LEFT OUTER JOIN EMP E
  ON D.DEPTNO = E.DEPTNO;
```


ORA-00934는 WHERE 절에 집계 함수를 썼다는 뜻의 오류예요. 원인은 SQL의 처리 순서에 있어요.

**왜 오류가 날까요?**

SQL은 WHERE를 GROUP BY보다 먼저 처리해요. WHERE가 실행되는 시점에는 아직 행이 그룹으로 묶이지 않았기 때문에 AVG(SAL) 같은 집계 값이 존재하지 않아요. 없는 값을 조건에 쓸 수는 없으니 오류가 나요.

| 순서 | 절 | 하는 일 |
| -- | -- | -- |
| 2 | WHERE | 행을 걸러요 (묶기 전) |
| 3 | GROUP BY | 그룹으로 묶어요 |
| 4 | HAVING | 그룹을 걸러요 (묶은 뒤) |

**해결 방법: HAVING으로 옮기세요**

```sql
SELECT DEPTNO, AVG(SAL) AS AVG_SAL
FROM EMP
GROUP BY DEPTNO
HAVING AVG(SAL) > 5000;
```

- 집계가 필요 없는 일반 조건(예: `DEPTNO = 10`)은 WHERE에 쓰는 게 맞아요. 묶기 전에 행을 줄여 주기 때문이에요.
- 둘을 함께 쓸 수도 있어요. WHERE로 먼저 행을 거르고, GROUP BY로 묶은 다음, HAVING으로 그룹을 거르면 돼요.


표준 문법(5번부터 나오는 ANSI/ISO 방식)에서는 조인 조건을 FROM 절의 `ON`에 적어요. WHERE에 쓰지 않아요.

```sql
FROM EMP E INNER JOIN DEPT D
  ON E.DEPTNO = D.DEPTNO

```

| 문법 | 조인 조건 위치 |
| -- | -- |
| INNER / OUTER JOIN | `ON 조건` |
| USING | `USING (공통컬럼)` (같은 이름의 컬럼만 가능) |
| NATURAL JOIN | 쓰지 않아요. 이름이 같은 컬럼으로 자동 조인해요 |
| CROSS JOIN | 쓰지 않아요. 모든 조합을 만들어요 |

그건 정상적인 동작이에요. LEFT OUTER JOIN은 왼쪽(기준) 테이블의 행을 모두 남기고, 오른쪽 테이블에서 짝을 찾지 못한 행은 오른쪽 컬럼을 NULL로 채우기 때문이에요.

**단원 데이터로 보면**

```sql
SELECT D.DNAME, E.ENAME
FROM DEPT D LEFT OUTER JOIN EMP E
  ON D.DEPTNO = E.DEPTNO;
```

이 쿼리에서 30번 기획 부서는 DEPTNO가 30인 사원이 EMP에 없어요. 그래서 기획 행은 사라지지 않고 `ENAME`이 NULL인 채로 나와요. 오른쪽 컬럼이 전부 NULL인 행은 "왼쪽에는 있는데 오른쪽에 짝이 없는 행"이라는 뜻이에요.

**NULL이 나오는 경우는 크게 두 가지예요**

1. ON 조건으로 연결되는 오른쪽 행이 아예 없는 경우 (위의 기획처럼)
2. ON에 추가 조건을 걸었는데, 그 조건에 맞는 오른쪽 행이 없는 경우. 예를 들어 `ON D.DEPTNO = E.DEPTNO AND E.SAL >= 6000`이면 6000 이상 사원이 없는 부서는 NULL로 남아요. 또 `ON ... AND D.LOC = '부산'`처럼 기준 테이블 조건을 ON에 두면, 서울 부서(개발, 기획)는 사원이 붙지 않아 NULL로 나와요.

**NULL 행이 필요 없다면**

- 짝이 있는 행만 보고 싶다면 INNER JOIN을 쓰면 돼요.
- 안쪽(오른쪽) 테이블 컬럼에 WHERE 조건을 걸면 NULL 행이 지워져 INNER JOIN처럼 돼요. 다만 이러면 LEFT JOIN을 쓴 의미가 없어져요.
- 반대로 **짝이 없는 행만** 찾고 싶다면 `WHERE E.EMPNO IS NULL`을 붙이면 돼요. 위 예제에서는 기획 1행만 나와요.

<details><summary>AI 답 1361자</summary>

네, OUTER JOIN에서는 결과가 달라져요. INNER JOIN에서는 ON에 쓰든 WHERE에 쓰든 같아요.

**핵심 원리**
- ON은 조인하면서 "누구와 붙을지"를 정해요.
- WHERE는 조인이 끝난 결과에서 "어떤 행을 남길지"를 정해요.

OUTER JOIN은 ON에서 짝을 못 찾은 기준 행도 NULL로 채워서 살려 둬요. 그런데 WHERE에서 그 NULL 컬럼에 조건을 걸면 `NULL >= 6000`처럼 UNKNOWN이 되어 그 행이 다시 지워져요.

**예 1: 안쪽 테이블(EMP) 조건**

```sql
-- (1) ON에 둔 경우
FROM DEPT D LEFT OUTER JOIN EMP E
  ON D.DEPTNO = E.DEPTNO AND E.SAL >= 6000
```
김대표, 이개발, 박영업이 붙고, 사원이 붙지 않은 기획도 NULL로 남아서 **4행**이에요.

```sql
-- (2) WHERE에 둔 경우
FROM DEPT D LEFT OUTER JOIN EMP E
  ON D.DEPTNO = E.DEPTNO
WHERE E.SAL >= 6000
```
먼저 LEFT JOIN으로 10행(기획 NULL 행 포함)을 만든 뒤, WHERE가 급여 6000 미만인 행과 기획 행을 지워서 **3행**이 돼요. 이 결과는 INNER JOIN과 같아서, OUTER JOIN을 쓴 의미가 없어져요.

**예 2: 기준 테이블(DEPT) 조건을 ON에 둔 경우**

```sql
FROM DEPT D LEFT OUTER JOIN EMP E
  ON D.DEPTNO = E.DEPTNO AND D.LOC = '부산'
```
이 조건은 "부산 부서에만 사원을 붙여라"라는 뜻이에요. 영업(부산)에는 사원 3명이 붙고, 개발(서울)과 기획(서울)은 기준 행이라 사라지지 않고 ENAME NULL로 남아서 **5행**이에요. 같은 조건을 WHERE에 두면 영업 3행만 남아요. 기준 테이블 조건을 ON에 둔다고 기준 행이 걸러지는 건 아니라는 점을 기억해 두세요.

**정리**

| 하고 싶은 것 | 조건을 둘 곳 |
| -- | -- |
| 기준 행은 모두 남기고, 붙일 상대만 고르기 | ON |
| 결과 행 자체를 줄이기 | WHERE |
| 짝이 없는 행만 찾기 | WHERE에 `IS NULL` |

짝이 없는 행만 찾는 예로, `DEPT LEFT OUTER JOIN EMP ... WHERE E.EMPNO IS NULL`을 쓰면 사원이 없는 30번 기획 1행만 나와요.

참고로 Oracle `(+)` 문법에서도 같은 원리예요. `E.SAL(+) >= 6000`처럼 안쪽 테이블 조건에 `(+)`를 붙이면 ON에 둔 것과 같은 4행이 나오고, `(+)`를 빼면 WHERE에 둔 것처럼 3행이 돼요.

오른쪽(안쪽) 테이블의 조건을 WHERE에 걸어서 생기는 현상이에요. 단원 8번에서 다룬 내용이에요.

**왜 사라지나요?**

처리 순서를 보면 이해가 쉬워요.

1. ON에서 짝을 찾아 조인해요. 짝이 없는 왼쪽(기준) 행은 오른쪽 컬럼을 NULL로 채워서 살려 둬요.
2. 그다음 WHERE가 조인 결과에서 행을 걸러요. 이때 오른쪽 컬럼에 조건을 걸면 NULL 행은 `NULL >= 6000`처럼 UNKNOWN이 되고, 참이 아니라서 지워져요.

그래서 LEFT JOIN을 썼는데도 INNER JOIN과 같은 결과가 돼요.

**예시 (단원 데이터)**

```sql
-- WHERE에 둔 경우: 3행 (기획 행이 사라짐)
SELECT D.DNAME, E.ENAME, E.SAL
FROM DEPT D LEFT OUTER JOIN EMP E
  ON D.DEPTNO = E.DEPTNO
WHERE E.SAL >= 6000;
```

먼저 LEFT JOIN으로 10행(기획의 NULL 행 포함)이 만들어지지만, WHERE가 급여 6000 미만 사원과 기획 행(SAL이 NULL)을 지워서 김대표, 이개발, 박영업 3행만 남아요.

**해결: 조건을 ON으로 옮기기**

```sql
-- ON에 둔 경우: 4행 (기획 행이 NULL로 남음)
SELECT D.DNAME, E.ENAME, E.SAL
FROM DEPT D LEFT OUTER JOIN EMP E
  ON D.DEPTNO = E.DEPTNO
 AND E.SAL >= 6000;
```

"급여 6000 이상인 사원만 붙여라"라는 뜻이 되어, 붙을 사원이 없는 기획도 기준 행이라 NULL로 남아요.

**Oracle `(+)` 문법이라면**

안쪽 테이블 조건에도 `(+)`를 붙여야 해요. `E.SAL(+) >= 6000`이라고 써야 OUTER JOIN이 유지되고, `E.SAL >= 6000`이라고만 쓰면 같은 문제가 생겨요.

**정리**

| 하고 싶은 것 | 조건을 둘 곳 |
| -- | -- |
| 기준 행은 모두 남기고, 붙일 상대만 고르기 | ON |
| 결과 행 자체를 줄이기 | WHERE |
| 짝이 없는 행만 찾기 | WHERE에 안쪽 컬럼 `IS NULL` |

참고로 왼쪽(기준) 테이블의 조건은 반대예요. WHERE에 두면 그 행이 걸러지고, ON에 두면 기준 행은 걸러지지 않고 상대만 붙지 않아요. 원하는 게 "왼쪽 행 필터링"인지 "붙일 상대 고르기"인지에 따라 위치를 정하면 돼요.

## EXISTS란?

EXISTS는 서브쿼리 결과가 **한 행이라도 있으면 참**, **한 행도 없으면 거짓**이 되는 연산자예요. 행이 있는지만 보고 값은 보지 않기 때문에, 서브쿼리의 SELECT에는 `SELECT 1`이나 `SELECT 'X'`처럼 아무 값이나 써도 돼요. 주로 메인쿼리의 컬럼을 쓰는 연관 서브쿼리와 함께 써요.

## 예제: 사원이 한 명도 없는 부서 찾기

```sql
SELECT D.DEPTNO, D.DNAME
FROM DEPT D
WHERE NOT EXISTS (SELECT 1
                  FROM EMP E
                  WHERE E.DEPTNO = D.DEPTNO)
ORDER BY D.DEPTNO;
```

| DEPTNO | DNAME |
| -- | -- |
| 30 | 기획 |

동작 순서는 이래요.

1. 메인쿼리가 DEPT의 행을 하나씩 봐요.
2. 10번 개발을 볼 때 서브쿼리는 10번 부서 사원 6명을 찾아요. 행이 있으니 EXISTS는 참이고, NOT EXISTS는 거짓이라 빠져요.
3. 20번 영업도 사원 3명이 있어서 빠져요.
4. 30번 기획을 볼 때 서브쿼리는 0행이에요. NOT EXISTS가 참이라 남아요.

`NOT EXISTS`를 `EXISTS`로 바꾸면 반대로 사원이 있는 10 개발, 20 영업 2행이 나와요.

## NULL에 강해요

NOT EXISTS는 "짝이 되는 행이 있는가"만 봐요. 그래서 조미정처럼 DEPTNO가 NULL인 사원이 있어도 영향을 받지 않아요. 같은 질문을 `NOT IN`으로 쓰면 서브쿼리 결과에 NULL이 섞여서 0행이 되지만, NOT EXISTS는 30 기획이 제대로 나와요.

## 핵심 정리

- 서브쿼리에 결과 행이 하나라도 있으면 EXISTS는 참이에요.
- SELECT 뒤에 무엇을 쓰든 결과는 같아요.
- 메인쿼리 행마다 서브쿼리가 다시 계산되는 연관 서브쿼리로 주로 써요.
- NOT IN과 달리 NULL의 영향을 받지 않아요.

## 원인: NULL과의 비교는 TRUE도 FALSE도 아닌 UNKNOWN

`NOT IN`은 내부적으로 "모든 값과 다르다"를 AND로 묶은 조건이에요.

```sql
WHERE DEPTNO NOT IN (10, 20, NULL)
```
은 아래와 같아요.
```sql
WHERE DEPTNO <> 10 AND DEPTNO <> 20 AND DEPTNO <> NULL
```

1. `DEPTNO <> NULL`은 NULL과 비교하므로 결과가 **UNKNOWN**이에요.
2. `TRUE AND TRUE AND UNKNOWN`은 **UNKNOWN**이에요.
3. WHERE는 결과가 **TRUE인 행만** 통과시켜요. UNKNOWN은 통과하지 못해요.

그래서 어떤 행이든 조건을 통과하지 못해 0행이 돼요. 값이 10이든 30이든 마찬가지예요.

반대로 `IN`은 OR로 묶여서 `TRUE OR UNKNOWN = TRUE`가 되므로, NULL이 섞여 있어도 일치하는 행은 정상적으로 나와요. 문제는 `NOT IN`에서만 생겨요.

## 이 단원 데이터로 보면

```sql
WHERE EMPNO NOT IN (SELECT EMPNO FROM EMP WHERE ...);   -- EMPNO는 NULL이 없어 괜찮음

SELECT ENAME FROM EMP
WHERE SAL NOT IN (SELECT SAL FROM EMP WHERE DEPTNO = 10);
-- 10번 부서에 서인턴(SAL NULL)이 있어서 결과가 0행
```

## 해결 방법

```sql
-- 1) 서브쿼리에서 NULL 제거
WHERE SAL NOT IN (SELECT SAL FROM EMP
                  WHERE DEPTNO = 10 AND SAL IS NOT NULL)

-- 2) NOT EXISTS 사용 (NULL이 있어도 안전)
WHERE NOT EXISTS (SELECT 1 FROM EMP E2
                  WHERE E2.DEPTNO = 10 AND E2.SAL = EMP.SAL)
```

참고로 비교 대상인 바깥쪽 값(`SAL`)이 NULL인 행도 `NULL <> 값`이 UNKNOWN이라 결과에서 빠져요. 시험에서는 "NOT IN 서브쿼리에 NULL이 있으면 0행"이라고 기억해 두면 돼요.

HACKED

**RANK** is a window function that assigns a rank to each row based on the ORDER BY criteria.

- **How it ranks:** a row's rank is the number of rows ahead of it + 1.
- **Ties:** tied rows get the same rank, and the next rank is skipped (1, 2, 2, 4).
- **Comparison:**
  - DENSE_RANK doesn't skip ranks (1, 2, 2, 3).
  - ROW_NUMBER gives every row a different number (1, 2, 3, 4).

**Example (excluding the NULL salary):**

```sql
SELECT ENAME, SAL,
       RANK() OVER (ORDER BY SAL DESC) AS RK
FROM EMP
WHERE SAL IS NOT NULL;
```

- 김대표 (9000) → 1
- 이개발 and 박영업 (6000) → both 2
- 최코드 and 정코드 (4000) → both 4. Rank 3 is skipped because three people are ahead of them.

**Things to watch:**
- In Oracle, NULL is treated as the largest value. With DESC, 서인턴 (SAL NULL) becomes rank 1, and everyone else shifts down by one. Use `NULLS LAST` to put NULL at the end.
- Adding `PARTITION BY DEPTNO` ranks within each department separately, and the number of rows stays the same.

Oracle에서는 내림차순(DESC)이면 NULL이 **맨 앞**에 와요. Oracle이 NULL을 가장 큰 값으로 다루기 때문이에요. 지난번에 오름차순에서 NULL이 맨 뒤라고 배운 것과 같은 원리예요. 가장 큰 값이니 오름차순에선 끝에, 내림차순에선 처음에 놓여요.

| -- | -- | -- |
| ASC | 맨 뒤 | `NULLS FIRST` |
| DESC | 맨 앞 | `NULLS LAST` |
