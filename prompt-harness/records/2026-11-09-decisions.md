# AI 프롬프트 개선: 정해야 할 것 12가지 (2026-11-09)

AI 프롬프트를 시험해서 더 나은 문장을 찾았지만, 서비스에 넣기 전에 사람이 정해야 할 것이 남아 있어요. 이 문서는 개발 배경이 없어도 각 결정이 무엇이고, 무엇을 고르면 어떻게 되는지 알 수 있도록 썼어요.

결정마다 아래 순서로 적었어요.

- **무엇을 정하나요:** 결정할 내용 한 문장
- **왜 정해야 하나요:** 지금 상황과 문제
- **선택지:** 고를 수 있는 것과 그 결과
- **추천:** 시험 결과에 근거한 제안
- **정하면 바뀌는 것:** 누가 무엇을 고치는지

## 먼저 알아 두면 좋은 말

| 말 | 뜻 |
| --- | --- |
| 프롬프트 | AI에게 주는 지시문이에요. "짧게 답해", "단원 내용만 써"처럼 AI가 어떻게 일할지 정해요. |
| 시험(검증) | 같은 질문 수십~수백 개를 지금 문장과 고친 문장으로 각각 돌려서, 상위 AI(Opus)가 정해진 기준으로 채점하게 했어요. |
| 단원 / 절 | 단원은 학습 화면 한 장(예: GROUP BY와 집계 함수), 절은 단원 안의 소주제(예: WHERE와 HAVING의 차이)예요. |
| keywords | AI가 질문 요약에 붙이는 검색용 단어 태그예요(예: COUNT, GROUP BY). |
| 기본 문제 | AI 없이 미리 만들어 등록해 둔 퀴즈 문제예요. AI가 문제를 못 만들 때 대신 내요. 지금 28개이고 모두 객관식이에요. |
| 핵심 요소(keyPoints) | 서술형 문제마다 붙는 채점 체크리스트예요(예: "COUNT(*)는 NULL도 센다", "AVG는 NULL을 빼고 나눈다"). |
| 라벨 | 사람이 미리 정해 둔 "이 답은 맞음/틀림"이에요. AI 채점이 맞았는지 비교하는 기준이에요. |
| ADR | 팀이 정한 설계 결정을 적어 둔 문서예요. 번호로 불러요(예: ADR 0010). |
| API / 구독 계정 | 서비스는 API로 AI를 불러요. API 사용 한도에 걸려서, 일부 시험은 구독 계정(Claude Code)으로 대신 했어요. 두 방식은 조건이 조금 달라요. |

## ① 답변

### 1. 답 길이 상한: 600자 또는 400자

- **무엇을 정하나요:** AI 답이 몇 자를 넘지 않게 할지 정해요.
- **왜 정해야 하나요:** 지금 AI 답은 평균 770자, 길면 1,500자예요. 학습 화면 옆 질문 창에서 스크롤이 길어지고, 묻지 않은 내용까지 붙어요. 추천 문장은 "3~6문장, 600자 이내"로 정해서 평균 336자가 됐어요.
- **선택지:**
  - **600자:** 시험을 마친 값이에요. 품질 통과율이 70.6%에서 98.5%로 올랐어요.
  - **400자:** 더 짧아지지만, 예시가 필요한 설명이 잘릴 수 있어요. 시험 도중 API 한도에 걸려 결과가 없어요.
- **추천:** 600자로 시작해요. 실제 사용에서 답이 길다는 의견이 나오면 400자를 시험해요.
- **정하면 바뀌는 것:** 지시문 안의 숫자 하나예요.

### 2. 다른 단원의 SQL 질문에 답할지

- **무엇을 정하나요:** 학습자가 지금 보는 단원 밖의 질문을 하면 어떻게 할지 정해요. 예: GROUP BY 단원을 보다가 "ROW_NUMBER랑 RANK는 뭐가 달라요?"라고 묻는 경우예요.
- **왜 정해야 하나요:** AI는 지금 보는 단원 본문만 근거로 받아요. 다른 단원 질문에는 근거 없이 답해야 해서 틀릴 위험이 커요. 실제로 시험에서 다른 단원의 정렬 규칙을 놓쳐 예시를 잘못 계산한 경우가 있었어요.
- **선택지:**
  - **짧게 답하고 "이 단원에서 다루지 않는 내용"이라고 알림:** 지금 추천 문장의 방식이에요. 학습자는 답을 얻지만, 가끔 틀릴 수 있어요.
  - **답하지 않고 해당 단원으로 안내:** 틀릴 위험은 없지만, 학습자가 답을 못 얻어요.
- **추천:** 짧게 답하고 알려요. SQL과 무관한 질문(예: 저녁 메뉴)에는 어느 쪽이든 답하지 않아요.
- **정하면 바뀌는 것:** 지시문의 "단원 밖 질문" 문장이에요.

### 3. 따로 쓰던 답변 원칙(4-65)과 합치는 방법

- **무엇을 정하나요:** 같은 답변 프롬프트를 두 곳에서 따로 만들었어요. 둘을 어떻게 하나로 합칠지 정해요.
  - 이번 시험에서 고른 추천 문장(v3-grounded)
  - Linear 4-65에서 쓰고 있는 답변 원칙 5가지, 빠른 질문 버튼, 드래그 메뉴, 말투 문장
- **왜 정해야 하나요:** 두 문장이 겹치는 부분(짧게 답하기, 말투)도 있고, 4-65에만 있는 부분도 있어요. 4-65 원칙 중 일부는 지금 AI에 보내지 않는 정보가 필요해요.
  - "이 개념, 11/5에도 물어보셨어요"라고 말하려면 과거 질문의 날짜가 필요해요.
  - "본문 2절을 참고하세요"라고 말하려면 절 번호와 제목이 필요해요.
  - 드래그한 문장으로 질문하려면 그 문장이 필요해요.
- **선택지:**
  - **추천 문장을 바탕으로 4-65 원칙을 더함:** 시험으로 확인한 품질을 지키면서 원칙을 넣을 수 있어요. 합친 뒤 한 번 더 시험해요.
  - **4-65 문장을 바탕으로 추천 문장의 규칙을 더함:** 기획 의도가 더 잘 드러나지만, 시험을 처음부터 다시 해야 해요.
- **추천:** 추천 문장을 바탕으로 합치고 다시 시험해요. 시험 도구가 이미 있어서, 합친 문장만 넣으면 돼요.
- **정하면 바뀌는 것:** 답변 지시문 전체가 바뀌어요. 필요하면 개발에서 과거 질문 날짜, 절 번호처럼 AI에 보내는 정보를 더해요.

### 4. 앞 대화를 몇 개까지 AI에 보낼지

- **무엇을 정하나요:** 학습자가 질문할 때 같은 대화창의 앞 질문과 답을 몇 개까지 AI에 함께 보낼지 정해요.
- **왜 정해야 하나요:** 지금은 같은 대화창의 앞 대화를 개수 제한 없이 모두 보내요. 다른 단원에서 한 대화도 섞여요. 대화가 길어질수록 AI 비용이 늘고 답이 느려지며, 관련 없는 앞 대화에 끌려갈 수 있어요. 디자인 시안은 "최근 8개"예요.
- **선택지:**
  - **제한 없음(지금):** 오래된 맥락까지 기억하지만, 비용과 속도가 대화 길이에 따라 늘어요.
  - **최근 8개:** 비용과 속도가 일정해져요. 9번째보다 오래된 대화는 AI가 기억하지 못해요.
- **추천:** 최근 8개예요. 긴 대화는 아직 시험하지 않았으므로, 정한 뒤 긴 대화 사례를 더해 시험해요.
- **정하면 바뀌는 것:** 개발에서 앞 대화를 가져오는 코드에 개수 제한을 더해요.

## ② 요약

### 5. 의미 없는 입력의 keywords를 코드로 지울지

- **무엇을 정하나요:** "ㅁㄴㅇㄹ"나 "김치찌개 레시피"처럼 학습과 무관한 질문의 요약에서 keywords를 코드로 지울지 정해요.
- **왜 정해야 하나요:** 질문의 주제를 찾지 못하면 서비스는 keywords로 비슷한 과거 질문을 찾아요. 의미 없는 질문에 "GROUP BY" 같은 태그가 붙으면, 나중에 GROUP BY를 물을 때 그 엉뚱한 질문의 요약이 AI에 함께 들어가요. 11/8에 "무관한 입력이면 keywords를 비운다"고 정했지만, 프롬프트만으로는 12건 중 6건만 비웠어요.
- **선택지:**
  - **프롬프트에만 맡김:** 고칠 코드는 없지만, 절반은 태그가 남아요.
  - **코드로 지움:** 확실하지만, 무엇을 "무관한 입력"으로 볼지 코드 규칙을 정해야 해요.
- **추천:** 코드로 지워요. 구체적인 규칙은 개발과 정해요.
- **정하면 바뀌는 것:** 요약을 저장하는 코드예요.

## ③ 퀴즈 생성

### 6. 결과표도 5행 이하로 제한할지

- **무엇을 정하나요:** 문제 안에 넣는 표를 3~5행으로 제한하는 규칙을 "실행 결과표"에도 똑같이 적용할지 정해요.
- **왜 정해야 하나요:** 문제는 화면에서 짧게 보이도록 표를 3~5행으로 제한해요. 그런데 "결과표를 보고 어떤 그룹 함수를 썼는지 고르기" 같은 절은 소계와 총계 행까지 보여 줘야 해서 6~9행이 필요해요. 지금 규칙대로면 AI가 규칙을 어기거나 문제가 성립하지 않아요.
- **선택지:**
  - **결과표는 예외로 허용:** 문제가 성립하지만, 화면에서 표가 길어져요.
  - **결과표도 5행 이하:** 화면은 짧지만, 일부 절은 좋은 문제를 내기 어려워요.
- **추천:** 결과표는 예외로 허용해요. 디자인에서 긴 표가 화면에 어떻게 보이는지 확인해 주세요.
- **정하면 바뀌는 것:** 퀴즈 생성 지시문의 표 규칙 문장이에요.

### 7. 객관식 보기 순서를 코드로 섞을지

- **무엇을 정하나요:** AI가 만든 객관식 보기의 순서를 저장할 때 코드로 무작위로 섞을지 정해요.
- **왜 정해야 하나요:** AI는 정답을 앞쪽 보기에 몰아 두는 경향이 있어요. 시험한 객관식 45문제에서 정답 위치가 1번 19개, 2번 17개, 3번 8개, 4번 1개였어요. 학습자가 "정답은 보통 1~2번"이라는 패턴을 알아챌 수 있어요.
- **선택지:**
  - **프롬프트로 "정답 위치를 고르게" 지시:** 효과가 확실하지 않아요.
  - **코드로 섞음:** 확실하게 고르게 나뉘어요.
- **추천:** 코드로 섞어요.
- **정하면 바뀌는 것:** 문제를 저장하는 코드예요. 섞은 뒤 정답 번호도 함께 맞춰요.

### 8. 빈칸·서술형 기본 문제를 등록할지

- **무엇을 정하나요:** 지금 모두 객관식인 기본 문제를 객관식, 빈칸, 서술형으로 나눠 등록할지 정해요.
- **왜 정해야 하나요:** 11/5 회의에서는 "기본 문제는 모두 객관식이어도 된다"고 정했어요(Linear 4-90). 11/9에 PO가 세 형식으로 나눠 등록하기로 했으므로, 이전 결정을 바꾼 기록이 필요해요. 형식별 기본 문제가 생기면 두 가지가 좋아져요.
  - AI가 문제를 못 만들 때 대신 내는 문제도 형식이 다양해져요.
  - 등록 문제를 AI에게 예시로 보여 주는 방법(퓨샷)을 실제 문제로 다시 시험할 수 있어요. 11/9에 AI가 만든 임시 문제로 시험했을 때는 뚜렷한 개선이 없어 보류했어요.
- **선택지:** 등록함(11/9 결정) / 지금처럼 객관식만.
- **추천:** 등록해요. Linear 4-90에 바뀐 결정을 남겨요.
- **정하면 바뀌는 것:** 기본 문제 데이터를 작성하고 검수해요. 등록한 뒤 예시 넣기 시험을 다시 해요.

## ④ 서술형 채점

### 9. 채점 기준: A(모두 담아야 맞음) 또는 B(절반 이상 담으면 맞음)

- **무엇을 정하나요:** 서술형 답을 언제 "맞음"으로 볼지 정해요.
- **왜 정해야 하나요:** 예를 들어 핵심 요소 5개 중 4개를 맞게 쓴 답이 있어요. 기준 A면 틀림, 기준 B면 맞음이에요. 지금 코드는 A, 디자인 시안과 Linear 4-99의 추천은 B예요. 두 기준에서 결과가 달라지는 답이 시험한 96건 중 20건이었어요.
- **선택지:**
  - **기준 A:** 엄격해요. 거의 다 맞게 쓴 학습자도 틀림을 받을 수 있어요.
  - **기준 B:** 너그러워요. 다만 절반 기준이 의미 있으려면, 퀴즈 생성 AI가 핵심 요소를 3개 이상 만들어야 해요.
  - 어느 쪽이든 틀린 내용이 섞이면 틀림이에요.
- **추천:** PO가 학습 경험을 보고 정해요. 추천 채점 방식(checklist)은 코드의 숫자 하나로 A와 B를 바꿀 수 있어서, 나중에 바꾸기도 쉬워요.
- **정하면 바뀌는 것:** 채점 코드의 설정값 하나예요. B로 정하면 퀴즈 생성 지시문에 "핵심 요소 3개 이상"을 더해요.

### 10. 핵심 요소(keyPoints)를 유지할지

- **무엇을 정하나요:** 서술형 문제마다 붙는 채점 체크리스트(핵심 요소)를 계속 쓸지 정해요.
- **왜 정해야 하나요:** 11/6 회의에서 핵심 요소를 없애기로 했지만, 코드가 아직 쓰고 있어서 당분간 유지 중이에요(Linear 4-90). 추천 채점 방식(checklist)은 핵심 요소마다 "담았는지"를 확인하는 방식이라, 핵심 요소가 없으면 쓸 수 없어요.
- **선택지:**
  - **유지:** checklist 방식을 쓸 수 있어요. 시험에서 라벨과 가장 잘 맞았고, 같은 답을 3번 채점해도 결과가 한 번도 바뀌지 않았어요.
  - **없앰:** AI가 모범 답만 보고 판정해야 해요. 이 방식은 시험하지 않았고, 기준 B의 "절반"을 셀 수 없어요.
- **추천:** 유지해요.
- **정하면 바뀌는 것:** 유지하면 바뀌는 것이 없어요. 없애면 채점 방식을 새로 시험해야 해요.

### 11. 애매한 라벨 12건 검수, ADR 0010 수정

- **무엇을 정하나요:** 두 가지를 정해요.
  - 채점 시험의 정답 라벨 중 애매한 12건이 맞는지 PO가 확인해요.
  - checklist 방식을 쓰려면 설계 결정 문서 ADR 0010을 고칠지 정해요.
- **왜 정해야 하나요:**
  - 라벨 96건은 AI가 초안을 만들었어요. 그중 12건은 사람마다 판단이 갈려요. 가장 큰 질문은 "문제가 묻지도 않은 핵심 요소가 빠졌을 때, 그 답을 틀렸다고 볼지"예요. 추천 방식이 지금 방식보다 앞선 차이가 모두 이 12건에서 나왔으므로, 라벨에 따라 결론이 바뀔 수 있어요.
  - ADR 0010 결정 3은 "AI는 맞음/틀림만 돌려준다"예요. checklist는 핵심 요소별 결과를 돌려주므로 이 결정을 고쳐야 해요. 요소별 결과를 저장할지도 함께 정해요. 저장하면 화면에서 "핵심 요소 5개 중 4개를 짚었어요"처럼 보여 줄 수 있어요.
- **추천:** 라벨을 먼저 검수하고, 결과에 따라 ADR을 고쳐요.
- **정하면 바뀌는 것:** checklist 채택 여부가 확정돼요. 검수 문서는 `records/2026-11-08-grading-labels-review.md`예요.

## 공통

### 12. API 한도를 올릴지, 12/1까지 기다릴지

- **무엇을 정하나요:** AI 사용 한도를 올려서 바로 최종 확인을 할지, 한도가 풀리는 12/1까지 기다릴지 정해요.
- **왜 정해야 하나요:** 11/8 오후에 회사 API 사용 한도에 걸려 AI 호출이 막혔어요. 그 뒤 요약, 퀴즈, 채점 시험은 구독 계정으로 대신 했어요. 구독 계정은 서비스와 조건이 조금 달라서, 버전 사이의 우열은 믿을 수 있지만 정확한 수치는 서비스에서 달라질 수 있어요. 그래서 서비스에 넣기 전에 API로 한 번 확인하는 것이 안전해요.
- **선택지:**
  - **한도를 올림:** 요약, 퀴즈, 채점을 바로 확인하고 반영할 수 있어요. 확인 비용은 약 $55예요.
  - **12/1까지 기다림:** 비용이 늘지 않지만, 그때까지는 API로 이미 확인한 것만 반영해요. 답변 추천 문장과 퀴즈의 "정보처리기사 → SQLD" 수정이 여기에 해당해요.
- **추천:** 한도를 올려요. 기다리는 동안에도 답변과 SQLD 수정은 먼저 반영할 수 있어요.
- **정하면 바뀌는 것:** 요약, 퀴즈, 채점을 서비스에 반영하는 시점이에요.
