# 질문 개념 분류 하네스

질문 개념 분류 프롬프트를 여러 버전으로 바꿔 가며, 같은 질문 세트로 정확도, 응답 시간, 토큰, 비용을 비교한다.

## 실행

이 폴더에서 아래 명령을 실행한다.

```bash
sh run.sh                                              # baseline 프롬프트 하나로 실행
sh run.sh prompts/baseline.json prompts/v2.json        # 두 버전을 같은 질문으로 비교
sh run.sh prompts/v2.json --questions my-questions.json # 다른 질문 세트로 실행
```

결과는 `results/`에 실행 시각을 이름으로 한 `.md`와 `.json`으로 쌓인다.

## 준비물

- 서비스 저장소 `silo-4th`를 이 저장소와 같은 폴더에 받아 둔다. 다른 위치라면 `SILO_4TH_REPO=경로 sh run.sh`로 실행한다.
- 서비스 저장소의 `.env.local`에 `ANTHROPIC_API_KEY`가 있어야 한다.
- 같은 저장소의 `.env.test.local`에 test 브랜치 `DATABASE_URL`이 있어야 한다. 개념 목록을 여기서 읽는다.
- 저장소에서 `npm install`을 한 번 해 두어야 한다.

## 파일

| 파일 | 내용 |
| --- | --- |
| `prompts/*.json` | 시험할 프롬프트. `baseline.json`은 서비스가 지금 쓰는 프롬프트다 |
| `questions.json` | 처음 만든 질문 10개 |
| `questions-full.json` | 개념 24개 전체를 패턴 8가지로 다룬 질문 106개. 개념 여러 개를 기대하는 문항이 있다 |
| `questions-single.json` | `questions-full.json`에서 기대값을 핵심 개념 하나로 바꾼 세트. 4-95 결정(11/6) 이후 기준 세트다 |
| `prompts/concept-notes.json` | 개념별 한 줄 정리. 단원 본문의 "개념 한눈에 보기" 표에서 뽑았다 |
| `harness.ts` | 분류를 돌리고 결과를 기록하는 본체 |
| `count-tokens.ts` | 서비스 흐름의 호출별 입력 토큰을 재는 스크립트 |

## 프롬프트 파일 만들기

`prompts/baseline.json`을 복사해서 `name`, `system`, `user`를 고친다.

- `{{CONCEPTS}}`는 DB에서 읽은 `개념ID: 개념 이름` 줄 목록으로 바뀐다.
- `conceptNotes`에 한 줄 정리 JSON 파일 경로(프롬프트 파일 기준)를 주면 줄 끝에 ` - 한 줄 정리`가 붙는다.
- `schema`를 주면 응답 형식을 바꾼다. 개념을 `conceptIds` 배열 대신 `conceptId` 하나로 받아도 된다.
- `{{QUESTION}}`은 질문 세트의 질문으로 바뀐다.
- 두 변수는 `system`과 `user` 어느 쪽에 넣어도 된다.
- JSON 안에서는 줄바꿈을 `\n`으로 쓴다.

## 판정 기준

- 일치: AI가 고른 개념 묶음이 기대한 묶음과 같다.
- 부분 일치: 하나 이상 겹치지만 묶음이 다르다.
- 불일치: 하나도 겹치지 않는다.
- 같은 프롬프트라도 실행마다 결과가 조금 달라질 수 있어서, 버전을 비교할 때는 두세 번 돌려 본다.

## 주의

- 호출 설정은 저장소의 `lib/llm/ask-json.ts`를 따라 만들었다. 저장소에서 모델, effort, 스키마가 바뀌면 `harness.ts`도 맞춰야 한다.
- 비용은 ADR 0007과 0008에 적힌 Haiku 5.5 가격, 100만 토큰당 입력 $0.10과 출력 $0.50으로 계산한다.

## 기록

### 2026-11-06: 개념 하나만 고르게 바꾸기 (4-95)

**배경**: 질문 하나에 가장 연관 있는 개념 하나만 붙이기로 정했다(11/6 결정). 지금 서비스 프롬프트는 관련 개념을 여러 개 고른다.

**질문 세트**: `questions-single.json`, 106문항. 개념 24개마다 용어 직접(P1), 상황 설명(P2), 증상(P3) 질문을 넣고, 개념 여러 개(P5), 목록 밖(P6), 맥락 의존(P7), 구어(P8) 질문을 더했다.

**정답 검수**: 미완료. #14, #81, #86, #104는 AI가 고른 개념이 맞을 수도 있어서 검수 중이다.

**결과**: 모델 `ANTHROPIC_UTILITY_MODEL`(Haiku 5.5), effort low, 프롬프트마다 두 번 실행

| 프롬프트 | 바꾼 점 | 일치 | 부분 일치 | 불일치 | 오류 | 1,000건 비용 |
| --- | --- | --- | --- | --- | --- | --- |
| `baseline` | 지금 서비스 그대로 | 76 / 76 | 26 / 26 | 4 / 4 | 0 / 0 | $0.12 |
| `single` | "최대 하나만" 지시 | 97 / 96 | 1 / 0 | 8 / 9 | 0 / 1 | $0.12 |
| `single-schema` | 지시 + 응답을 `conceptId` 하나로 제한 | 99 / 99 | 0 / 0 | 7 / 7 | 0 / 0 | $0.13 |
| **`single-notes`** | 지시 + 개념 한 줄 정리 | **101 / 101** | 1 / 1 | 4 / 4 | 0 / 0 | $0.30 |
| `single-schema-notes` | 지시 + 한 줄 정리 + 응답 제한 | 101 / 97 | 0 / 0 | 5 / 8 | 0 / 1 | $0.30 |

결과 파일: `results/2026-11-06T08-40-27.md`, `08-47-20.md`(baseline, single, single-schema), `08-58-47.md`, `09-02-47.md`(notes 두 버전)

**알게 된 것**

- 개념 이름만으로는 단서가 부족하다. "반환 결과에 따른 분류"라는 이름만으로는 ANY/ALL, 다중 컬럼 질문을 연결하지 못했다. 한 줄 정리를 붙이자 맞게 됐다.
- 응답 형식에 `null`을 허용하면, 맞던 질문에도 `null`을 돌려주는 경우가 생겨 결과가 흔들렸다.
- "하나만" 지시를 넣어도 배열 응답에서 두 개를 고르는 경우가 106건 중 1건 있었다.
- 한 줄 정리 때문에 입력 토큰이 926에서 약 2,700으로 늘지만, 응답 시간은 평균 1.1~1.4초로 거의 같다.

**서비스 반영 제안**

1. system 프롬프트를 `prompts/single-notes.json`의 내용으로 바꾼다.
2. 개념 목록을 `ID: 이름 - 한 줄 정리` 형식으로 넘긴다. 한 줄 정리를 어디에 둘지(`concepts` 컬럼, 본문, 상수)는 서비스 쪽에서 정한다.
3. 응답 스키마는 `conceptIds: string[]`로 두고, 저장할 때 목록에 있는 첫 번째 ID 하나만 넣는다.

**4-95 완료 기준**: `questions-single.json` 기준으로 baseline이 76/26/4다. 서비스에 반영한 뒤 101/1/4 이상이면 된다. 이슈에 적힌 86/16/4는 기대값을 바꾸기 전 세트(`questions-full.json`)로 잰 숫자라서 비교 기준으로 쓰지 않는다.
